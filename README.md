# Clarion

社内向けツール。「録る → AIが『なぜ』を聞く → 言語化ドキュメント化 → AIロープレ教材」の4段階のうち、
**②のファシリテーション（何を、どう聞くか）が唯一の差別化要素**という整理に基づき、質問生成のプロンプトを中核に据えている。

```
docs/     フロントエンド（GitHub Pages にそのまま置ける静的ページ。ビルド不要）
worker/   バックエンド（Cloudflare Worker + D1。APIキーの隠蔽、データ保管、STT→LLM→TTS の集約）
tools/    監視カメラ映像から音声を抽出する一括変換スクリプト
```

## 全体構成

| 層 | 使うもの | 役割 |
| --- | --- | --- |
| フロント | GitHub Pages（素のHTML/JS） | 3タブUI。データは端末のlocalStorageに保存 |
| バック | Cloudflare Worker | APIキー隠蔽、クライアント別トークン認証、1リクエストへの集約 |
| 言語 | Claude API | 転換点抽出・質問生成・判断基準統合・客のセリフ生成・採点 |
| 音声入力 | Whisper API（OpenAI） | MediaRecorderで録った音声をテキスト化 |
| 音声出力 | Aivis Cloud API ／ OpenAI TTS（差し替え可能） | 客のセリフを読み上げ |

ロープレの1ターンは `録音 → Worker → Whisper → Claude → TTS → {transcript, replyText, audioUrl}` を
1リクエストで返す。直列処理なので1ターン数秒。リアルタイム通話ではなく練習なので許容範囲、という判断。
`audioUrl` はdata URIで返る（フロント側でBlob URLに変換して再生）。

現場向けの使い方は [MANUAL.md](MANUAL.md) にある。以下は構成と設置の説明。

## 3つのステップ

```
  ① 蓄積 ──────→ ③ 統合 ──────→ ② ロープレ
  接客を溜める    判断基準に束ねる   モードで練習する
     ↑                                    │
     └──────── フィードバック ←────────────┘
```

1. **蓄積** — 案件を1件ずつ溜める。接客の書き起こしを貼る（音声ファイルからの書き起こしも可）と、
   AIが転換点を3〜5個検出し、本人へのインタビュー質問を作る。回答を書き込み、浅ければ「もう一段掘る」で
   追加質問を生成する。**ここでは判断基準を作らない。事実と本人の言葉を溜めることに徹する。**
2. **ロープレ** — 統合済みの判断基準から作った**モード**（判断基準 × 客タイプ × 場面 × 声）を選んで練習する。
   終了すると判断基準を唯一の評価軸として採点する（一般的な接客マナーでは加点減点しない）。
   採点後に**フィードバック**（AI客の再現度／採点の納得感／自由コメント）を返す。
3. **統合** — 複数の案件を選んで判断基準ドキュメントに束ねる。このとき、2で溜まったフィードバックを
   同時に読み込ませる。「客が素直すぎる」「ここは的外れ」といった現場の指摘が、次の版の判断基準に反映される。

②で返したフィードバックが③に入り、③の結果が②のモードになる。この往復でナレッジが更新されていく。

### データの持ち方

案件・判断基準・モード・実施記録はすべて **Cloudflare D1** に入る。端末を変えても同じデータが見える。
ブラウザに残るのは接続設定と実施者名だけ。**投入した音声は書き起こしたら破棄され、保存しない。**

### 客タイプの2トラックと、折れる条件

分岐表は書いていない。毎ターン生成で、会話の経路は決めていない。
代わりに型ごとに「**何が揃えば客が折れるか**」を3つと「**それをご破算にする禁じ手**」を1つ持たせている
（`CUSTOMER_TYPES` の `flags` / `breaker`）。経路は自由、条件だけ固い、という作り。

| トラック | 型 | 開始状態 |
|---|---|---|
| `standard` | 迷い客・価格重視・寡黙・知識豊富・不満・買取相談・同伴者あり（7） | 買う／売ると決めに来ている |
| `reversal` | 見せに来ただけ（1） | **売る気がない。**条件が揃ったときだけ翻る |

成約の二値だけだと不成約の回がすべて同じ顔になるので、採点で「どの条件まで立ったか」を
引用つきで返させている。不成約でも「2/3 到達」が残る。

条件は**一度立っても禁じ手で外れる**。`stateOf()` は最後のターンの状態を現在地とし、
一度でも立ったかは `everMet` で別に数えて採点に渡す。

`showoff` の3条件は現場から出してもらったもの。残り7型はこちら側の草案なので、
現場感覚と違えば `prompts.js` の `flags` を直す。ロープレも採点も同時に追随する。

### 心境と、声の自動追随

客の発話は `roleplayTurnRequest` で構造化して返させ、セリフと一緒に
**そのターン終了時の心境（`MOODS` の7状態）と条件の達成状況**を受け取る。

これを次のターンのシステムプロンプトに戻し、同時に読み上げの演技にも渡す
（`voiceDirection(customerType, mood)` が型の地声に心境を重ねて
OpenAI TTSの `instructions`、Aivisの `emotional_intensity` と `speaking_rate` を作る）。
これが無いと、不満客は20ターン目でも1ターン目と同じ声で苛立ったままになる。

心境は受講者にも返す（**表情**として画面に出す）。対面なら顔で分かることなので、
音声だけの都合で奪わない。条件の達成状況は返さない（`visibleHistory` で落とす）。そちらは答え。

構造化に失敗したときは素のテキスト生成に落ちて会話を続ける。心境は直前のまま据え置く。

### 品物と相場

ロープレの品物は**商品マスタ**から引く。AIに想像させると型番も相場も毎回変わり、採点の基準にならないため。

マスタが持つのは `新品価格` と `買取率（美品での買取率%）` の2つだけ。
実施のたびに**状態ランク**（新品同様〜難あり）と**付属品**（完備／一部／本体のみ）を振り、
`新品価格 × 買取率 × 状態係数 × 付属品係数` で**その回の正解額**を計算する。計算は `worker/src/items.js`。

買取率を商品ごとに持たせているのは、商材で桁が違うため。ロレックスや終売のウイスキーは100を超え、
量販の家電やファッションジュエリーは10〜20にしかならない。単一の係数では正解額が現場とずれる。

正解額の判定は**AIに任せない**。AIの仕事は会話から「店員が提示した金額」を抜き出すところまでで、
減点はコードが決める（`pricePenalty`）。採点のたびに正解が揺れないようにするため。

**受講者には採点が終わるまで品物も正解額も見えない。**
`POST /api/runs` は品物を返さず、`GET /api/runs` は未採点の回を `{hidden:true}` に伏せる（`visibleItem`）。
モード一覧もカテゴリしか返さない。`GET /api/products` は指導者以上に限る（相場表そのものなので、
品物が分かった時点で正解を逆算できてしまう）。

### 権限とデータの分離

ログインは **会社コード + 共通パスワード + 個人コード** の3点。ReCOREの入り方に寄せてある。
パスワードは会社共通なので、個人コードは本人確認ではなく「どこまで見せるか・触らせるか」の切り分け。

| | 受講者 trainee | 指導者 trainer | 管理者 admin |
|---|:---:|:---:|:---:|
| ②ロープレ・自分の記録 | ○ | ○ | ○ |
| 会社全員の記録 | — | ○ | ○ |
| ①蓄積・判断基準の本文 | — | ○ | ○ |
| ③統合・モード作成・マスタ編集・スタッフ管理 | — | — | ○ |

分離の軸は2本ある。

- **ナレッジ空間**（`companies.knowledge_space`）… 案件・判断基準・モード・商品・用語。同じ値の会社どうしで共有される
- **会社コード**（`runs.client`）… 実施記録。**必ず会社ごとに分かれる**

2社が同じ教材で練習し、点数と会話ログは互いに見えない、という運用がこれ。
判断基準の実施回数も自社の分しか数えない。③の統合に読み込むフィードバックも自社の分だけ。

パスワードは PBKDF2-SHA256（10万回）。セッショントークンはSHA-256にして保存するので、
DBが漏れてもそのままでは使えない。有効期間は既定14日（`SESSION_DAYS` で変更可）。

### 移行前からの共有トークン

`ACCESS_TOKENS` の共有トークンも引き続き通る。この入口で入った管理者は
**どの会社のスタッフも操作できる**（会社を作ってコードを配る立場なので、ここを塞ぐと初期設定ができない）。
ログインで入った管理者は自分の会社だけ。

```
ACCESS_TOKENS = "clarion:みんなの共有トークン,clarion:管理者トークン"
ADMIN_TOKENS  = "管理者トークン"
```

会社コードを配る運用に移ったら、共有トークンは配布をやめる。

## セットアップ

### 1. Worker と D1 をデプロイ

```bash
cd worker
npm install
npx wrangler d1 create clarion          # 出力された database_id を wrangler.jsonc に書く
npx wrangler d1 execute clarion --remote --file=schema.sql
# 既存のDBに後から足す場合は、差分だけを流す（schema.sql は ALTER が二重に走るので流せない）
# npx wrangler d1 execute clarion --remote --file=migrate-products-auth.sql
npx wrangler secret put ANTHROPIC_API_KEY
npx wrangler secret put OPENAI_API_KEY
npx wrangler secret put AIVIS_API_KEY        # 音声合成にAivisを使う場合のみ（既定はopenaiなので不要）
npx wrangler secret put ACCESS_TOKENS   # 例: clientA:長いランダム文字列,clientB:別の文字列
npx wrangler deploy
```

`wrangler.jsonc` の `ALLOWED_ORIGINS` は、フロントを配信するGitHub PagesのURL（`https://<ユーザー名>.github.io`）に絞ってある。
オリジンが変わったらここを直して再デプロイする。
音声合成の選び方は次節。

ローカル開発は `cp .dev.vars.example .dev.vars` して値を埋め、`npm run dev`。
外部APIを叩かない疎通テストは `npm test`。

### 2. フロントを公開

リポジトリの Settings → Pages で、ブランチ `main` / フォルダ `/docs` を選ぶだけ。ビルド工程はない。

### 3. 会社とスタッフを作る

運用系は練習画面と分けて `docs/admin/` に置いてある（`/Clarionx/admin/`）。
現場で練習する人と運用する人では見るものが違い、設定タブに全部を積むと
受講者が触る画面に相場表とスタッフ一覧のコードが載ることになるため。

共有トークン（`ACCESS_TOKENS`）で管理者として入り、管理コンソールで

1. **会社**を登録する（会社コード・会社名・パスワード・ナレッジ空間）。2社で教材を共有するならナレッジ空間を同じ値にする
2. **スタッフ**を追加する（個人コード・氏名・店舗・権限）
3. **商品マスタ**の「サンプル100点を読み込む」を押し、買取率を現場の相場に合わせて直す

管理コンソールの正解額の試算は `GET /api/products/:id/quote` を叩いていて、
計算はWorker側の `priceFor` をそのまま呼ぶ。画面側に式を写すと本番の採点とずれるため。

以降は各自が会社コード・パスワード・個人コードでログインする。
セッショントークンは端末のlocalStorageにのみ保存される。iPad/iPhoneのSafariでの利用を想定。

## 音声合成（TTS）の差し替え

当初はにじボイスAPIを使っていたが、**2026年2月4日にサービス終了**したため差し替えた。
同じことが起きても1ファイルで済むよう、`worker/src/audio.js` の `PROVIDERS` にプロバイダを分離してある。

| プロバイダ | 設定 | 性格 |
| --- | --- | --- |
| `openai`（既定） | `OPENAI_API_KEY`（Whisperと共用） | 追加の契約が要らず、これだけで鳴る。`instructions` で客の演技を指示できる。日本語の自然さは国産勢に一歩劣る |
| `aivis` | `AIVIS_API_KEY` と `AIVIS_MODEL_UUID` | 日本語ネイティブ。感情表現あり、¥440/万文字。ACMLライセンスのモデルはクレジット表記不要 |
| `none` | — | 読み上げを止める。フロントは端末の `speechSynthesis` で代替する |

既定は `openai`。Whisper用に必ず要る `OPENAI_API_KEY` だけで鳴るので、音声のために別の契約をしなくてよい。
日本語の読み上げの質を上げたくなった時点で `TTS_PROVIDER` を `aivis` に変える。失敗したら音声なしで会話だけ続く。
客タイプごとの読み上げの演技指示は `worker/src/prompts.js` の `CUSTOMER_TYPES`（`voice` と `intensity`）にある。
不満客なら語気を強める、寡黙な客なら抑揚を抑える、といった調整はここ。

別のプロバイダを足すときは `PROVIDERS` に `{ enabled, voices, synthesize }` を持つエントリを1つ追加するだけでよい。

## 音声の準備（監視カメラ映像から）

```bash
./tools/extract-audio.sh ./recordings ./audio
```

映像は不要なので音声だけ抜く。16kHz・モノラルWAVなら70時間でも8GB程度。
Whisper APIの上限が1ファイル25MBなので、既定で15分ごとに分割する（`SEGMENT_SECONDS` で変更可）。

監視カメラのマイクは天井付け・無指向性で距離があるため、専用レコーダーより精度は落ちる。
書き起こしは目視で直してから①に流すこと。

## 運用上の注意

- **目的外利用の確認**：元々「防犯・監視」目的で録画された音声をAI研修データに転用する形になる。
  録画を保有する側での確認が済むまで、本番データを流さないこと。
- **TTSベンダーへの依存**：にじボイスの終了で一度作り直している。特定の1社に直結させないこと。
  Aivisのモデルを使う場合、モデルごとのライセンス（ACML以外を選ぶとクレジット表記が要る場合がある）を確認する。
- **データの置き場所**：現状すべて端末のlocalStorage。顧客ごとにデータを分ける／判断基準を隠す段階になったら、
  Worker側にKVかD1を足してサーバ保存へ移す。認証はすでにクライアント別トークンで入っている。
- **コスト**：判断基準の統合と採点は精度優先で Opus、ロープレの1ターン生成はレイテンシ優先で Sonnet
  （`worker/src/llm.js` の `MODELS`）。音声合成は Aivis が¥440/万文字（月額¥1,980の無制限プランもあり）。

## プロンプトを直す場所

`worker/src/prompts.js` に集約してある。特に `INTERVIEW_SYSTEM`（誘導しない・一度に二つ聞かない・
専門用語を持ち込まない・抽象化させない）が、このツールの価値そのもの。現場で効かない質問が出たら、まずここを直す。
